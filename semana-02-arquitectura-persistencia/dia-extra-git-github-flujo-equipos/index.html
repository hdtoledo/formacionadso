Por qué fracasan los proyectos en grupo

Lo que pasa sin reglas vs. cómo trabaja la industria

Antipatrones que rompen entregas

  • "Te mando el ZIP por WhatsApp": nadie sabe cuál archivo es el más reciente (proyecto_final_v3_ahora_si.zip).
  • Todos empujan a main: un compañero sube código roto el día de la sustentación y daña el trabajo de los otros 3.
  • Un solo computador sube todo: no queda trazabilidad de quién aportó qué y en la empresa eso es inadmisible.
  • Subir .env o node_modules/: contraseñas expuestas en internet y repositorios de 300 MB imposibles de clonar.

Estándar de ingeniería en equipos de 2–4

  • Un solo repositorio fuente de verdad: todos clonan el mismo repo y sincronizan antes de empezar cada tarea.
  • Ramas aisladas por tarea: cada quien trabaja en su rama feat/...; si algo falla, main y develop siguen intactas.
  • Pull Request + Code Review: ningún código entra sin que al menos 1 compañero lo lea y apruebe.
  • Historial limpio y auditable: cada commit lleva autor real, propósito claro y 0 secretos.

¿Quién lidera el proyecto? Roles y revisión cruzada

Regla de los 4 ojos: el rol de Tech Lead / Maintainer se puede rotar cada sprint para que todos aprendan a administrar GitHub, pero nadie aprueba ni fusiona su propio Pull Request sin revisión.
Gobernanza del repositorio

Tech Lead / Maintainer: lo que SÍ lidera y lo que NO hace

Responsabilidades del Tech Lead

  • 1. Inicializar el repo: crea el repositorio, agrega .gitignore, plantilla de PR y la rama develop.
  • 2. Configurar seguridad: invita colaboradores con permisos claros y activa Branch Protection Rules en main y develop.
  • 3. Coordinar la arquitectura: define la estructura de carpetas para que dos personas no reescriban el mismo archivo sin aviso.
  • 4. Cuidar la integración: desbloquea conflictos complejos, exige pruebas en cada PR y lidera el PR final develop → main.

Lo que el Tech Lead NO debe hacer

  • No es un "jefe que no programa": también desarrolla tareas en sus propias ramas feat/... y pasa por revisión de un compañero.
  • No recibe archivos por chat para subirlos él: cada integrante hace sus propios commits y su propio git push.
  • No desactiva la protección de main por prisa: las prisas antes de una entrega son cuando más se rompen los proyectos.
  • No aprueba PRs sin leer el diff: dar "Approve" a ciegas convierte el Code Review en un trámite inútil.
Consejo real para fichas ADSO: definan el mapa de módulos antes de escribir código (ej. quién toca auth, quién catalog, quién frontend). Menos solapamiento de archivos = menos conflictos de merge.
Modelo recomendado: Git Flow simplificado

Las 5 ramas que entiende cualquier empresa

Rama Nace desde Se fusiona en Propósito real ¿Protegida?
main Inicial — Código estable de producción / entrega evaluable. Siempre funciona. SÍ · Bloqueada
develop main main (por sprint) Integración continua del equipo. Aquí se juntan y prueban las features. SÍ · Solo PR
feat/* develop develop Una funcionalidad concreta (feat/auth-login). Se borra tras merge. No · Temporal
fix/* develop develop Corrección de un bug detectado en pruebas (fix/validacion-ruc). No · Temporal
hotfix/* main main y develop Parche de emergencia en producción (ej. fallo crítico en vivo). No · Urgente

¿Y GitHub Flow? Si el equipo es de 2 personas con despliegue continuo y pruebas automatizadas en cada PR, pueden omitir develop y fusionar feat/* → main directo vía PR. En ADSO, main + develop da un colchón seguro antes de cada sustentación.

Trazabilidad profesional

Nombres de ramas y Conventional Commits

Cómo nombrar ramas (minúsculas + guiones)

# Bien: prefijo + módulo + objetivo corto
feat/auth-registro-usuarios
fix/catalogo-filtro-categoria
docs/readme-instalacion-local
# Mal: nombres personales o genéricos
rama-juan / nueva / pruebas2 / Final_OK

Por qué: en GitHub cualquier compañero sabe qué hace una rama sin abrirla. Nunca use espacios, tildes ni mayúsculas en nombres de rama.

Conventional Commits: tipo(alcance): verbo

# Commits atómicos (1 cambio lógico por commit)
feat(auth): validar correo duplicado con codigo 409
fix(ui): corregir desborde de tabla en movil 360px
refactor(db): extraer pool de postgres a config/db.js
test(api): agregar coleccion bruno del catalogo
# Evitar siempre
"cambios" / "arregle cosas" / "avance viernes"

Regla práctica: si al describir el commit necesita escribir "y además...", probablemente debió dividirlo en dos commits.

La unidad real de colaboración en GitHub

Qué lleva un Pull Request (PR) que sí da gusto revisar

1. Dirección correcta

Verifique arriba: base: develop ← compare: feat/.... El error #1 en aula es abrir el PR contra main.

2. Tamaño pequeño

Un PR de 150 líneas se revisa en 5 minutos y detecta bugs. Un PR de 2.000 líneas nadie lo lee bien.

3. Evidencia real

Si cambió API → captura de Bruno en verde. Si cambió UI → captura en móvil y escritorio.

Plantilla automática: si guarda este archivo en .github/pull_request_template.md, GitHub lo carga solo en cada PR nuevo.
.github/pull_request_template.md PLANTILLA REAL 
## ¿Qué resuelve este Pull Request?
<!-- Explique en 2 o 3 líneas el cambio y qué tarea o módulo cubre -->

## Tipo de cambio
- [ ] `feat`: nueva funcionalidad
- [ ] `fix`: corrección de un error
- [ ] `refactor`: mejora interna sin cambiar comportamiento
- [ ] `docs`: documentación o guías

## ¿Cómo se probó?
<!-- Indique los comandos ejecutados, capturas o casos de Bruno en verde -->
- [ ] Probado localmente sin errores en consola
- [ ] Probado con Bruno / navegador (adjuntar captura si cambia la UI)

## Checklist antes de pedir revisión
- [ ] Mi rama salió actualizada desde `develop` (no tiene conflictos)
- [ ] No incluí archivos `.env`, contraseñas ni `node_modules/`
- [ ] Los commits siguen Conventional Commits (`feat(...)`, `fix(...)`)
- [ ] Revisé mi propio diff en GitHub antes de asignar revisor
Cultura de ingeniería · Revisión de pares

Code Review: los 3 veredictos y qué revisar primero

Comment

Comentar sin bloquear

Preguntas aclaratorias o sugerencias menores de estilo que no impiden fusionar.

Request changes

Pedir ajustes antes del merge

Cuando hay un bug, falta validación, viene un .env o rompe una ruta. El autor hace otro commit en la misma rama y el PR se actualiza solo.

Approve

Aprobar para integración

El código cumple requisitos, es seguro y claro. Desbloquea el botón de merge en GitHub.

Checklist rápido del revisor (en orden de prioridad)

1. Seguridad: ¿hay secretos, .env, SQL concatenado o entradas sin validar?
2. Funcionalidad: ¿resuelve lo pedido y maneja errores (400/404/500)?
3. Impacto: ¿borró accidentalmente código de otro compañero?
4. Respeto: critique el código, nunca a la persona ("Sugiero validar X" en vez de "Esto está mal").
Los 3 botones de integración en GitHub

¿Qué opción de Merge elegir al aprobar un PR?

Squash and merge

RECOMENDADO feat/*

Aplasta todos los commits intermedios de la rama ("fix typo", "ajustes review") en 1 solo commit limpio sobre develop.

Cuándo usarlo: en todos los PR de feat/* y fix/* hacia develop.

Create a merge commit

RECOMENDADO release

Conserva todos los commits individuales de la rama y agrega un commit de unión con los dos padres.

Cuándo usarlo: al integrar develop → main al cierre del sprint para conservar el historial de cada PR.

Rebase and merge

AVANZADO

Reescribe cada commit de la rama encima de la punta de destino sin crear commit de merge (historial 100% lineal).

Cuándo usarlo: solo cuando cada commit individual ya está impecable y el equipo domina Git.
Hábito de industria: después de fusionar un PR, siempre borre la rama feat/* (active Automatically delete head branches en Settings). El código ya vive en develop.
Las reglas que no dependen de la memoria

Los 3 candados técnicos del repositorio

1. Branch Protection

En GitHub → Settings → Branches para main y develop:

  • Require a pull request before merging
  • Require approvals: 1
  • Do not allow bypassing (aplica también al Tech Lead)
  • Block force pushes

2. .gitignore desde el día 1

Evita filtrar secretos y dependencias pesadas:

node_modules/
.env
server/.env
dist/
*.log

3. .github/CODEOWNERS

Asigna revisores automáticamente según la carpeta modificada:

*           @tech-lead
/server/    @dev-backend
/client/    @dev-frontend

Paso 1 de 9 · Lo ejecuta únicamente el Tech Lead

Crear el repositorio base y publicar develop

  1. 1. En GitHub: clic en + → New repository. Nombre: equipo-XX-git-lab.
  2. 2. Inicialización limpia: marque Add a README file y en .gitignore template seleccione Node.
  3. 3. Commit base en main: clone el repo, copie .gitignore y .github/pull_request_template.md, agregue ## Equipo a README.md y haga push a main antes de activar candados.
  4. Verificación: en GitHub, main ya tiene la plantilla PR y el selector de ramas muestra main y develop.
# PowerShell · Tech Lead
git clone https://github.com/<usuario-lead>/equipo-XX-git-lab.git
cd equipo-XX-git-lab

# Copiar .gitignore y .github/pull_request_template.md + preparar README
New-Item -ItemType Directory -Force .github
Add-Content README.md "`n## Equipo`n"
git add .gitignore .github/pull_request_template.md README.md
git commit -m "chore(repo): agregar gitignore, plantilla pr y seccion equipo"
git push origin main

# Crear y publicar la rama de integración
git switch -c develop
git push -u origin develop
Salida esperada: Branch 'develop' set up to track 'origin/develop'.
Paso 2 de 9 · Configuración en GitHub (Tech Lead)

Agregar colaboradores y activar el candado en GitHub

A. Invitar a los 2–4 integrantes

  1. Abra el repo → Settings → Collaborators.
  2. Clic en Add people → escriba el usuario exacto de GitHub de cada compañero.
  3. Cada compañero abre su correo o la campana de GitHub y hace clic en Accept invitation.
Error frecuente: si un compañero intenta git push sin aceptar la invitación, GitHub devuelve 403 Permission denied.

B. Proteger main y develop

  1. Settings → Branches → Add branch protection rule (o Rules → Rulesets).
  2. Patrón: main → marque Require a pull request before merging y Require approvals (1).
  3. Marque Do not allow bypassing the above settings.
  4. Repita la misma regla para develop.
  5. En Settings → General active Automatically delete head branches.

Clonar el repositorio y confirmar identidad local

Paso 4 de 9 · Antes de iniciar cualquier tarea

Ritual de arranque: pull de develop → nueva rama

# SIEMPRE estos 3 comandos antes de escribir una sola línea
git switch develop
git pull origin develop
git switch -c feat/perfil-carlos

# Confirmar en qué rama está parado (el * debe estar en feat/...)
git branch

¿Por qué git switch en lugar de checkout?

Git moderno separó switch (cambiar/crear ramas) de restore (deshacer cambios en archivos). Es más claro y evita borrar trabajo por error.

Error clásico: crear feat/b estando parado dentro de feat/a. Eso mezcla dos tareas en el mismo PR. Vuelva siempre a develop primero.
Paso 5 de 9 · Guardar y publicar su rama

Inspeccionar, commitear y subir solo su rama

# 1. Ver qué archivos cambió (¡jamás haga git add . a ciegas!)
git status
git diff

# 2. Agregar archivos concretos y hacer commit descriptivo
git add integrantes/carlos.md README.md
git commit -m "feat(equipo): agregar ficha de carlos y actualizar readme"

# 3. Subir la rama a GitHub por primera vez (-u enlaza el tracking)
git push -u origin feat/perfil-carlos

Qué hace -u (--set-upstream)

Le dice a Git qué rama remota corresponde a su rama local. Si luego el revisor pide cambios, en los siguientes commits solo escribe git push.

Verificación inmediata: la terminal imprime un enlace directo https://github.com/.../pull/new/feat/... y GitHub muestra el botón amarillo Compare & pull request.
Paso 6 de 9 · Interacción Autor ↔ Revisor en GitHub

Abrir el Pull Request y responder cambios solicitados

Flujo del Autor del PR

  1. Clic en Compare & pull request.
  2. Cambie base a develop (verifique: base: develop ← compare: feat/...).
  3. Complete título Conventional, descripción, evidencia y checklist.
  4. En la columna derecha, asigne al menos 1 compañero en Reviewers.
  5. Clic en Create pull request.

Si el revisor pide ajustes (Request Changes)

NO cierre el PR ni cree una rama nueva. Corrija en su misma rama local y haga push:

# Parado en la misma rama feat/perfil-carlos
git add integrantes/carlos.md
git commit -m "fix(equipo): completar rol segun code review"
git push

El PR en GitHub se actualiza automáticamente con el nuevo commit; luego haga clic en Re-request review.

Paso 7 de 9 · Cerrar el ciclo limpio

Aprobar, fusionar y limpiar ramas locales

1. En GitHub (PR en verde)

Con la aprobación del revisor y 0 conflictos, haga clic en Squash and merge → Confirm squash and merge.

2. Borrar rama remota

Si no activó el borrado automático, clic en Delete branch. Mantener 25 ramas viejas confunde al equipo.

3. Avisar al equipo: "PR #12 fusionado en develop, hagan pull antes de empezar su próxima rama".
# En PowerShell (el autor y cualquier compañero del equipo)
git switch develop
git pull origin develop

# Eliminar la rama local que ya fue fusionada
git branch -d feat/perfil-carlos

# Limpiar referencias a ramas remotas ya borradas en GitHub
git fetch --prune

app.use('/api/health', healthRoutes);
<<<<<<< HEAD
app.use('/api/auth', authRoutes);
=======
app.use('/api/content', contentRoutes);
>>>>>>> origin/develop

Seleccione una opción (A, B o C) para probar el resultado

Un conflicto no es un error grave: es Git pidiendo criterio humano porque dos personas modificaron exactamente la misma zona del archivo.

# Comandos tras guardar el archivo limpio (sin <<<< ni ====)
git add server/src/app.js
git commit -m "chore(merge): resolver conflicto en app.js"
git push
Paso 9 de 9 · Cierre de Sprint / Entrega al instructor

Promover develop → main y etiquetar la versión

Cuándo y cómo pasar a main

  1. Verifique que develop compila, levanta el servidor y pasa todas las pruebas Bruno sin fallos.
  2. El Tech Lead abre un PR: base: main ← compare: develop.
  3. Otro integrante verifica el resumen del sprint y marca Approve.
  4. Se integra con Create a merge commit (para preservar el rastro de cada PR del sprint) y NO se borra develop.
# Etiquetar la entrega oficial (SemVer: vMAJOR.MINOR.PATCH)
git switch main
git pull origin main
git tag -a v1.0.0 -m "Entrega Sprint 1: API dual + catalogo"
git push origin v1.0.0
Ventaja en sustentación: el instructor puede revisar exactamente qué había en v1.0.0 aunque el equipo ya esté trabajando en el Sprint 2 sobre develop.

Botiquín Git: qué hacer cuando algo sale mal

Accidente en aula Salida segura (PowerShell)
1. rejected (non-fast-forward) git pull origin <rama> ; # resolver conflicto si hay ; git push
2. Hice commits en develop sin crear rama git switch -c feat/mi-tarea ; git branch -f develop origin/develop
3. Agregué .env con git add (sin push) git restore --staged .env # (o git rm --cached .env si ya hubo commit)
4. Subí un secreto con git push Rote la contraseña/llave de inmediato (borrar el archivo no la saca del historial), luego límpiela del repo.
5. Necesito deshacer un commit ya publicado git revert <hash> # crea un commit inverso sin reescribir historia

Visor de Plantillas Git & GitHub

Autoevaluación · 3 preguntas · sin IA ni apuntes

¿Qué tanto dominas el flujo de Git & GitHub en equipo?

Responde antes de la sustentación. Cada opción muestra al instante si es correcta y por qué: úsala para detectar qué repasar.

En un equipo de 3 personas con main y develop protegidas, terminaste tu tarea en feat/auth-login. ¿Hacia qué rama abres el Pull Request?

  • Directo hacia main para ahorrar pasos
  • Hacia develop (base: develop ← compare: feat/auth-login) y asignas a un compañero como revisor
  • Haces git push --force origin develop
  • Envías la carpeta comprimida al Tech Lead para que él la suba

Tu Pull Request muestra un conflicto en server/src/app.js porque otro compañero registró una ruta en la misma línea. ¿Cuál es la forma correcta de resolverlo?

  • Elegir "Accept Current Change" para conservar solo tu código
  • Cerrar el PR y crear otro repositorio
  • Traer origin/develop a tu rama, integrar ambas rutas limpiando <<<<<<<, ======= y >>>>>>>, hacer commit y push
  • Ejecutar git push --force origin main

Un compañero revisa tu PR y marca Request changes pidiendo validar un campo. ¿Qué debes hacer?

  • Cerrar el PR y abrir uno nuevo desde otra rama
  • Corregir el código en la misma rama feat/..., hacer un nuevo commit y git push: el PR se actualiza automáticamente
  • Desactivar la protección de ramas para fusionar sin aprobación
  • Editar directamente la rama main en GitHub

Resumen: lo que se llevan hoy

Un líder organiza el repo y los candados, todos trabajan en ramas feat/* desde develop, nadie aprueba su propio PR, los conflictos se resuelven integrando el trabajo del equipo y main siempre está lista para presentar.

Reto opcional (equipos que terminan antes)

Agreguen .github/CODEOWNERS con sus usuarios reales y un flujo básico de GitHub Actions que ejecute node --check en cada Pull Request antes de permitir el merge.
