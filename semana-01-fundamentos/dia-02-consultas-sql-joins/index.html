ARQUITECTURA DEL MOTOR SQL · Modelo Mental Crítico

¿Cómo Ejecuta MySQL una Consulta Realmente?

El mayor error del aprendiz novato es asumir que SQL se ejecuta en el orden en que se escribe (SELECT primero). El motor relacional sigue un pipeline estricto de 8 fases:

1. FROM

Carga tablas base

2. ON / JOIN

Cruza relaciones

3. WHERE

Filtra filas base

4. GROUP BY

Agrupa filas

5. HAVING

Filtra grupos

6. SELECT

Calcula y proyecta

7. ORDER BY

Ordena filas

8. LIMIT

Página conjunto

¿Por qué falla esto en MySQL? 
-- ❌ ERROR 1054: Unknown column 'subtotal_con_iva' in 'where clause'
SELECT nombre, (precio * 1.19) AS subtotal_con_iva
FROM productos
WHERE subtotal_con_iva > 100000;

Motivo: El WHERE (Fase 3) se ejecuta mucho antes de que el SELECT (Fase 6) cree el alias subtotal_con_iva.

Solución Correcta y Profesional 
-- ✅ Repetir la expresión matemática en WHERE o usar Subconsulta/HAVING
SELECT nombre, (precio * 1.19) AS subtotal_con_iva
FROM productos
WHERE (precio * 1.19) > 100000;

El optimizador de InnoDB calcula el filtro directamente sobre la columna física sin depender de alias aún no generados.

FILTRADO DE FILAS · Precedencia de Operadores

Filtros con WHERE: La Trampa del AND vs OR

En el álgebra booleana de SQL, el operador AND tiene mayor prioridad de evaluación que el operador OR (similar a la multiplicación frente a la suma). No usar paréntesis provocará fugas de datos y reportes erróneos.

❌ CASO INCORRECTO (Sin Paréntesis) 
-- Queremos aprendices ACTIVOS de Garzón o Neiva:
SELECT nombre, ciudad, activo 
FROM usuarios
WHERE activo = 1 AND ciudad = 'Garzón' OR ciudad = 'Neiva';

Resultado inesperado: Trae todos los usuarios activos de Garzón, ¡PERO también trae a María Rojas aunque esté INACTIVA porque la condición de la derecha (ciudad = 'Neiva') se evalúa aislada!

✅ CASO CORRECTO (Paréntesis Obligatorios) 
-- Agrupando la condición lógica de ciudades:
SELECT nombre, ciudad, activo 
FROM usuarios
WHERE activo = 1 
  AND (ciudad = 'Garzón' OR ciudad = 'Neiva');

Comportamiento real: Primero resuelve si el usuario es de Garzón o Neiva, y de ese grupo EXIGE obligatoriamente que activo = 1.

Regla SENA ADSO: Siempre que combines AND con OR, encapsula los grupos de decisión entre paréntesis para asegurar claridad para ti y para el motor relacional.
Precedencia booleana en bases de datos relacionales
PATRONES Y RANGOS · Filtros de Alto Rendimiento

Patrones (LIKE), Listas (IN) y Rangos (BETWEEN)

Escribir consultas profesionales implica evitar ristras interminables de comparaciones con OR usando operadores nativos optimizados:

1. LIKE (Comodines % y _)

% representa 0 o más caracteres.
_ representa exactamente 1 caracter. 

-- Correos institucionales:
SELECT nombre, email 
FROM usuarios
WHERE email LIKE '%@misena.edu.co';

-- Códigos que inician con 'LAP-':
SELECT * FROM productos
WHERE codigo LIKE 'LAP-%';
2. IN (Pertenencia a Conjuntos)

Reemplaza múltiples OR haciéndolo más legible y permitiendo subconsultas posteriores. 

-- En vez de: ciudad = 'A' OR ciudad = 'B'
SELECT nombre, ciudad 
FROM usuarios
WHERE ciudad IN ('Garzón', 'Neiva', 'Pitalito');

-- Estados específicos:
SELECT codigo, total 
FROM pedidos
WHERE estado IN ('PAGADO', 'ENVIADO');
3. BETWEEN (Rangos Inclusivos)

Equivale a val >= min AND val <= max (incluye ambos límites). 

-- Rango de precios:
SELECT nombre, precio 
FROM productos
WHERE precio BETWEEN 400000 AND 2000000;

-- Rango de fechas:
SELECT codigo, fecha 
FROM pedidos
WHERE fecha BETWEEN '2026-09-01' 
                AND '2026-09-30';
Tip de Rendimiento: Evita iniciar búsquedas LIKE con porcentaje al principio (%texto) en tablas con millones de registros, pues anula el uso de índices B-Tree obligando a un Table Scan completo.
Operadores DQL estándar SQL-92
LÓGICA TRIVALENTE · Pregunta Clásica de Entrevista Técnica

La Gran Trampa de NULL en Bases de Datos

En bases de datos relacionales, NULL no es un valor. No es el número 0, no es espacio en blanco, ni es una cadena vacía ''. Representa el estado de ausencia de información o valor desconocido.

❌ ¿Por qué "= NULL" NUNCA funciona? 
-- Este query devuelve 0 filas SIEMPRE:
SELECT * FROM productos WHERE categoria_id = NULL;

-- Este query TAMBIÉN devuelve 0 filas SIEMPRE:
SELECT * FROM productos WHERE categoria_id != NULL;
¿Por qué? Cualquier comparación aritmética con NULL evalúa a UNKNOWN (desconocido). Y la cláusula WHERE solo devuelve filas que evalúen estrictamente a TRUE.
✅ Sintaxis Correcta: IS NULL & Manejo Seguro 
-- 1. Comparación con operadores de identidad:
SELECT nombre, precio 
FROM productos 
WHERE categoria_id IS NULL;

-- 2. Sustitución de nulos con IFNULL / COALESCE:
SELECT 
  nombre, 
  IFNULL(categoria_id, 0) AS cat_id_segura,
  COALESCE(categoria_id, 999) AS cat_con_default
FROM productos;

COALESCE() es el estándar ANSI SQL preferido porque acepta N parámetros y retorna el primer valor no nulo de la lista.

Regla de oro: Jamás uses = NULL. Usa siempre IS NULL o IS NOT NULL.
Lógica trivalente (TRUE, FALSE, UNKNOWN)
MÉTRICAS Y ESTADÍSTICAS · Reducción de Datos

Funciones de Agregación: De Filas a Indicadores

Las funciones de agregación toman un conjunto de valores de una columna y calculan un único valor resumen escalar:

COUNT()

Conteo de registros

SUM()

Suma aritmética

AVG()

Promedio aritmético

MIN()

Valor mínimo

MAX()

Valor máximo

Diferencia Crítica: COUNT(*) vs COUNT(columna) 
SELECT 
  COUNT(*) AS total_productos_bd,
  COUNT(categoria_id) AS con_categoria
FROM productos;

• COUNT(*) retorna 7 (cuenta filas totales).

• COUNT(categoria_id) retorna 6 (ignora el cable que tiene categoría NULL).

Métricas de Pedidos en Producción 
SELECT 
  COUNT(id) AS cantidad_pedidos,
  SUM(total) AS venta_total_global,
  ROUND(AVG(total), 2) AS ticket_promedio,
  MIN(total) AS pedido_mas_pequeno,
  MAX(total) AS pedido_mas_grande
FROM pedidos;

Usamos ROUND(..., 2) para formatear valores decimales monetarios evitando decimales infinitos.

SEGMENTACIÓN ANALÍTICA · Agrupamiento de Dimensiones

GROUP BY: Consolidando Reportes por Dimensión

Las funciones de agregación por sí solas dan un total global. Cuando queremos ver métricas por categoría, por ciudad o por estado, entra en acción GROUP BY.

Ejemplo: Ventas por Estado de Pedido 
SELECT 
  estado, 
  COUNT(id) AS cantidad_pedidos,
  SUM(total) AS total_recaudado
FROM pedidos
GROUP BY estado;
Salida esperada:
estado cantidad_pedidos total_recaudado
PAGADO3$ 6.850.000,00
PENDIENTE1$ 3.150.000,00
⚠️ La Regla de Oro (ONLY_FULL_GROUP_BY)

En MySQL 8.0 está activado por defecto el modo estricto ONLY_FULL_GROUP_BY.

Regla Absoluta:

Toda columna que pongas en el SELECT que NO esté dentro de una función agregada (SUM, COUNT, etc.), TIENE QUE ESTAR en la cláusula GROUP BY.

Si intentas seleccionar SELECT estado, fecha, SUM(total) ... GROUP BY estado, MySQL rechazará la consulta porque la fecha es ambigua para el grupo.

Estándar SQL ANSI / MySQL 8.0
FILTRO DE FILAS VS FILTRO DE GRUPOS · Claridad Conceptual Definitiva

El Gran Duelo: WHERE vs HAVING

Una de las preguntas que más aprendices reprueban en pruebas técnicas. Ambos filtran, pero en momentos y sobre conjuntos completamente distintos:

Característica WHERE HAVING
¿Cuándo se ejecuta? Fase 3: ANTES de agrupar Fase 5: DESPUÉS de agrupar
¿Sobre qué actúa? Sobre filas individuales de las tablas Sobre los grupos generados por GROUP BY
¿Admite funciones agregadas? ❌ NUNCA (ej. WHERE SUM(total) > 100 da error) ✅ SÍ (diseñado expresamente para eso)
Consulta Combinada con Ambos Filtros: 
SELECT 
  ciudad,
  COUNT(id) AS total_clientes,
  SUM(activo) AS clientes_activos
FROM usuarios
WHERE email LIKE '%@%'               -- 1. WHERE filtra usuarios individuales válidos
GROUP BY ciudad                      -- 2. GROUP BY consolida por ciudad
HAVING COUNT(id) >= 2;               -- 3. HAVING filtra las ciudades con 2 o más clientes

ALERTA DE SEGURIDAD Y RENDIMIENTO · Peligro de Colapso de Servidor

Anatomía de un JOIN y el Peligro del Producto Cartesiano

Un JOIN combina registros de dos o más tablas usando una condición explícita de coincidencia (ON). Si olvidas la condición, ocurre la peor catástrofe de un DBA:

⚠️ EL FATAL PRODUCTO CARTESIANO (CROSS JOIN) 
-- ❌ Sintaxis obsoleta o sin condición ON:
SELECT * FROM usuarios, pedidos; 
-- o también:
SELECT * FROM usuarios CROSS JOIN pedidos;

Multiplica cada fila de la tabla A por cada fila de la tabla B:

10.000 usuarios × 50.000 pedidos = 500.000.000 filas

Resultado: Agotamiento de memoria RAM, CPU al 100% y caída del servidor en producción.

✅ SINTAXIS MODERNA EXPLÍCITA (ANSI SQL-92) 
-- Siempre usa JOIN con su cláusula ON explícita:
SELECT 
  u.nombre AS cliente,
  p.codigo AS pedido
FROM usuarios u
INNER JOIN pedidos p 
  ON u.id = p.usuario_id; -- Condición de coincidencia

Tres Reglas Profesionales:

1. Usa siempre alias cortos y semánticos (u, p, prod).

2. Prefija todas las columnas (u.id, nunca id suelto).

3. Pon la llave foránea conectando a la llave primaria en el ON.

Control estricto de cardinalidad relacional
CRUCE EXACTO · Teoría de Conjuntos: Intersección (A ∩ B)

INNER JOIN: Solo Coincidencias en Ambas Tablas

Retorna únicamente los registros donde el valor de la columna en la Tabla A coincide con el de la Tabla B. Si un registro no tiene pareja en el otro lado, se descarta silenciosamente:

usuarios
pedidos
INNER

Solo aprendices/clientes que sí tienen al menos un pedido registrado.

Live Coding en Clase: 
SELECT 
  usr.nombre AS cliente,
  usr.ciudad,
  ped.codigo AS num_pedido,
  ped.total,
  ped.estado
FROM usuarios usr
INNER JOIN pedidos ped 
  ON usr.id = ped.usuario_id
WHERE ped.estado = 'PAGADO'
ORDER BY ped.total DESC;
¿Dónde quedó Valentina Losada (Usuario 4)? Como nunca ha hecho pedidos, el INNER JOIN la excluyó del listado.
Intersección estricta de claves foráneas
AUDITORÍA RELACIONAL · Preservación de la Tabla Izquierda

LEFT JOIN: Preservar Todo y Detectar Huérfanos

Trae absolutamente todas las filas de la tabla izquierda (FROM). Si la fila no tiene coincidencia en la tabla derecha, rellena los campos de la derecha con NULL:

1. Todos los clientes con o sin compras: 
SELECT 
  u.id, 
  u.nombre, 
  p.codigo AS pedido,
  IFNULL(p.total, 0.00) AS total_gastado
FROM usuarios u
LEFT JOIN pedidos p ON u.id = p.usuario_id;

Aquí Valentina aparecerá en el reporte con pedido = NULL y total_gastado = 0.00.

2. Técnica de Auditoría: "¿Quién NUNCA ha comprado?" 
-- Filtramos donde la llave de la derecha sea NULL:
SELECT u.id, u.nombre, u.email
FROM usuarios u
LEFT JOIN pedidos p ON u.id = p.usuario_id
WHERE p.id IS NULL AND u.rol_id = 3;

Esta consulta es el corazón de los sistemas CRM para enviar campañas de reactivación a usuarios inactivos.

¿Y el RIGHT JOIN? En el estándar corporativo moderno rara vez se usa RIGHT JOIN; se prefiere invertir el orden de las tablas en el FROM para leer siempre de izquierda a derecha.
Patrón de exclusión anti-join
INTEGRACIÓN COMPLETA · Cadena de Relaciones

Cruce Multitabla: Reporte Maestro de Facturación

En sistemas reales de producción como ERPs o pasarelas de pago, los datos requeridos residen en 4 o 5 tablas diferentes. Aprende a encadenar relaciones sin perder el hilo:

Encadenamiento Relacional: pedidos → usuarios → detalle_pedidos → productos → categorias 
SELECT 
  ped.codigo AS factura,
  ped.fecha,
  usr.nombre AS cliente,
  prod.nombre AS item,
  COALESCE(cat.nombre, 'General') AS categoria,
  det.cantidad,
  det.precio_unitario,
  det.subtotal
FROM pedidos ped
INNER JOIN usuarios usr        ON ped.usuario_id = usr.id
INNER JOIN detalle_pedidos det ON ped.id = det.pedido_id
INNER JOIN productos prod      ON det.producto_id = prod.id
LEFT JOIN categorias cat       ON prod.categoria_id = cat.id
ORDER BY ped.fecha DESC, det.id ASC;
Observa el detalle: Usamos LEFT JOIN en categorias porque algunos productos (como cables de prueba) pueden tener categoría NULL y no queremos que la factura desaparezca.
