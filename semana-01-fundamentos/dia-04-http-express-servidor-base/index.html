El Ciclo Request - Response: Arquitectura Cliente-Servidor

HTTP (Hypertext Transfer Protocol) es el protocolo de capa de aplicación sobre TCP/IP que rige la web. Es un modelo Stateless (sin estado): cada interacción es independiente y el servidor no guarda memoria implícita de la petición anterior.

1. Cliente (Consumer)

Un navegador web, una app móvil o un cliente de pruebas (Bruno / Postman). Inicia la conexión resolviendo el DNS, establece un socket TCP y envía un paquete formateado en texto plano.

HTTP Request (Petición)

2. Servidor (Producer)

Proceso activo en Node.js escuchando en un puerto (ej. 3000). Procesa la ruta solicitada, ejecuta middlewares, consulta la base de datos y genera una respuesta semántica.

HTTP Response (Respuesta)

3. Principio Stateless

El servidor trata cada petición como completamente nueva. Si el cliente no envía credenciales (Headers) o identificadores, el servidor no sabe quién es ni qué hizo antes.

Sin Memoria de Sesión Implícita
REGLA REST Toda petición debe contener toda la información requerida para ser entendida y procesada por el servidor.
RFC 9110 · HTTP Semantics
BLOQUE 1 Protocolo HTTP · Estructura de Mensaje
SLIDE 03 / 21

Anatomía de una Petición HTTP: Start Line, Headers y Body

Una petición HTTP es texto plano estructurado en tres secciones obligatorias separadas por retornos de carro (\r\n).

MENSAJE RAW TRANSMITIDO POR EL SOCKET TCP HTTP/1.1 
POST /api/productos HTTP/1.1
Host: localhost:3000
User-Agent: Bruno/1.38.0
Content-Type: application/json
Accept: application/json
Authorization: Bearer eyJhbGciOi...

{
  "nombre": "Teclado Mecánico RGB",
  "precio": 120000,
  "categoria": "HARDWARE"
}

Nótese la línea en blanco obligatoria entre el último Header y el inicio del Body.

1 Línea de Petición (Request Line)

Define tres elementos: el Método o Verbo (POST), el Target / Ruta (/api/productos) y la versión del protocolo (HTTP/1.1).

2 Encabezados (Headers)

Metadatos clave-valor. Content-Type: application/json le avisa al servidor cómo decodificar el Body, y Authorization transporta credenciales o tokens.

3 Cuerpo del Mensaje (Payload / Body)

Datos transmitidos por el cliente (POST, PUT, PATCH). En APIs modernas se serializan como cadenas JSON y requieren un middleware para ser leídos en Express.

Los métodos GET y DELETE convencionalmente no deben incluir cuerpo (Body); sus datos viajan en la URL mediante Params o Query Strings.

SLIDE 04 / 21

Verbos HTTP y el Principio de Idempotencia

Un método es Idempotente si ejecutarlo $N$ veces consecutivas produce exactamente el mismo estado en el servidor que ejecutarlo una sola vez.

Verbo Propósito REST ¿Seguro? (Safe) ¿Idempotente? Ejemplo en la API ADSO
GET Consultar o leer un recurso o colección SÍ SÍ GET /api/productos
POST Crear un nuevo recurso o disparar una acción NO NO POST /api/productos
PUT Reemplazar completamente un recurso existente NO SÍ PUT /api/productos/:id
PATCH Modificar parcialmente campos específicos de un recurso NO DEPENDE PATCH /api/productos/:id/stock
DELETE Eliminar un recurso identificado por ID NO SÍ DELETE /api/productos/:id
¿Por qué POST no es idempotente? Si un usuario hace clic 3 veces seguidas en "Pagar", se crearían 3 transacciones diferentes en la base de datos a menos que se use una clave de idempotencia.

Códigos de Estado HTTP: Las Familias RFC

Un error recurrente en juniors es devolver 200 OK con un objeto JSON que dice {"error": true}. El cliente HTTP no podrá detectar fallos automáticamente.

2xx ÉXITO
  • 200 OK: Solicitud procesada y cuerpo retornado (GET, PUT, PATCH).
  • 201 Created: Recurso creado exitosamente (POST).
  • 204 No Content: Éxito sin cuerpo de retorno (DELETE).
res.status(200).json(...)
3xx REDIRECCIÓN
  • 301 Moved Permanently: La URI cambió para siempre.
  • 304 Not Modified: El recurso no cambió desde la última petición en caché (ETag).
Uso en CDNs & Browsers
4xx ERROR CLIENTE
  • 400 Bad Request: JSON malformado o campos requeridos ausentes.
  • 401 Unauthorized: Falta token o no es válido.
  • 404 Not Found: Ruta o ID de recurso inexistente.
res.status(404).json(...)
5xx ERROR SERVIDOR
  • 500 Internal Error: Excepción no capturada (throw new Error).
  • 502 Bad Gateway: Servidor proxy no recibió respuesta válida.
  • 503 Unavailable: Servidor sobrecargado o en mantenimiento.
try / catch global
💡 Regla de Oro en ADSO: Si el ID no existe en la base de datos, el código HTTP OBLIGATORIO es 404 Not Found. Status Code Semántico

Inicialización del Proyecto con ECMAScript Modules (ESM)

En Node.js moderno abandonamos la sintaxis heredada de CommonJS (require()) para adoptar el estándar internacional de módulos import / export.

1. Comandos en Terminal PowerShell

# 1. Crear carpeta y entrar
mkdir mi-api-express && cd mi-api-express

# 2. Inicializar package.json
npm init -y

# 3. Instalar Express 4.x/5.x
npm install express
Recarga Automática (Node 18+): Puedes ejecutar tu servidor con node --watch server.js sin necesidad de instalar nodemon.

2. Modificación Clave en package.json

{
  "name": "mi-api-express",
  "version": "1.0.0",
  "type": "module", // <-- Habilita import / export
  "scripts": {
    "dev": "node --watch server.js",
    "start": "node server.js"
  },
  "dependencies": {
    "express": "^4.19.2"
  }
}

Al declarar "type": "module", Node.js procesará todos los archivos .js con el motor V8 nativo de módulos ES2022+, exactamente igual que en el frontend con React o Vite.

Preparado para escribir código homogéneo tanto en el servidor (Node/Express) como en el cliente (Navegador/React).
BLOQUE 1 Express.js · Servidor Mínimo Funcional
SLIDE 07 / 21

Estructura del Servidor Base & Primer Endpoint

Con apenas 15 líneas de código levantamos un servidor HTTP capaz de recibir miles de peticiones asíncronas concurrentes.

server.js ESM · Express 5 
import express from 'express';

// 1. Instancia de la aplicación
const app = express();
const PORT = process.env.PORT || 3000;

// 2. Primer Endpoint de Diagnóstico (Health Check)
app.get('/api/status', (req, res) => {
  res.status(200).json({
    ok: true,
    mensaje: "Servidor Express ADSO en funcionamiento",
    uptimeSegundos: Math.floor(process.uptime()),
    timestamp: new Date().toISOString()
  });
});

// 3. Poner a escuchar en el socket TCP
app.listen(PORT, () => {
  console.log(`🚀 Servidor activo en http://localhost:${PORT}`);
});

1. const app = express()

Crea el contenedor central donde se registrarán las rutas, middlewares y controladores.

2. app.get(ruta, handler)

Asocia el verbo GET a la URL /api/status. El handler recibe los objetos req (petición entrante) y res (respuesta saliente).

3. app.listen(PORT, callback)

Enlaza el socket TCP en el puerto 3000 y activa el bucle de eventos (Event Loop) en espera ininterrumpida de peticiones entrantes.

BLOQUE 2 Express.js · Procesamiento de Payload
SLIDE 10 / 21

El Middleware Crítico: express.json()

Node.js recibe los paquetes HTTP como flujos binarios (Buffer). Si no usamos un middleware parseador, Express no podrá leer el cuerpo de las peticiones POST o PATCH.

SIN app.use(express.json())

ERROR FATAL

El cliente envía un JSON en el Body, pero en la ruta Express:

app.post('/api/productos', (req, res) => {
  console.log(req.body); // >> undefined !
  // TypeError: Cannot destructure property 'nombre' of req.body as it is undefined
});

La aplicación arroja un error 500 o rompe el flujo porque req.body no existe.

El 90% de los juniors tropieza con este error

CON app.use(express.json())

ESTÁNDAR CORRECTO

El middleware intercepta cada petición antes de llegar a las rutas:

const app = express();

// Intercepta Content-Type: application/json
app.use(express.json());

app.post('/api/productos', (req, res) => {
  console.log(req.body); // >> { nombre: "Teclado", precio: 120000 }
});

Concatena los buffers entrantes, aplica JSON.parse() y deposita el objeto JavaScript en req.body.

Habilitar SIEMPRE antes de declarar las rutas
⚙️ Regla de Arquitectura: Coloca app.use(express.json()) en las primeras líneas tras instanciar app. Middleware Global
BLOQUE 2 Endpoint 1 · GET con Query Strings
SLIDE 11 / 21

Endpoint 1: GET /api/productos?categoria=...

Los parámetros de consulta (req.query) viajan tras el signo ?. Son ideales para filtros, búsquedas y paginación opcionales sin modificar la estructura de la ruta.

Código Express.js Captura req.query 
// Listar productos con filtro opcional
app.get('/api/productos', (req, res) => {
  const { categoria } = req.query;
  let resultado = productos;

  if (categoria) {
    resultado = productos.filter(p => 
      p.categoria.toUpperCase() === categoria.toUpperCase()
    );
  }

  res.status(200).json({
    ok: true,
    total: resultado.length,
    filtros: { categoria: categoria || "todos" },
    datos: resultado
  });
});

Si el cliente no envía ?categoria=..., req.query.categoria es undefined y retorna la lista completa.

Endpoint 2: GET /api/productos/:id (200 vs 404)

Los parámetros de ruta (req.params) identifican un recurso específico. Siempre se reciben como string y deben convertirse a Number() si el ID es numérico.

Código Express.js Captura req.params.id 
app.get('/api/productos/:id', (req, res) => {
  // 1. Casting a Number (obligatorio)
  const idBuscado = Number(req.params.id);
  
  // 2. Búsqueda en el array
  const producto = productos.find(p => p.id === idBuscado);

  // 3. Caso No Encontrado: Status 404
  if (!producto) {
    return res.status(404).json({
      ok: false,
      error: `Producto con ID ${idBuscado} no existe`
    });
  }

  // 4. Caso Exitoso: Status 200
  res.status(200).json({ ok: true, dato: producto });
});

El return dentro del if es vital para evitar el error Cannot set headers after they are sent.

BLOQUE 2 Endpoint 3 · Creación de Recursos con Body JSON
SLIDE 13 / 21

Endpoint 3: POST /api/productos (201 vs 400)

Para crear registros leemos los datos desde req.body. Debemos validar los campos requeridos antes de guardar y retornar el status semántico 201 Created.

Código Express.js Validación y Creación 
app.post('/api/productos', (req, res) => {
  const { nombre, precio, categoria, stock } = req.body;

  // 1. Validación defensiva (400 Bad Request)
  if (!nombre || !precio || precio <= 0) {
    return res.status(400).json({
      ok: false,
      error: "El nombre y el precio positivo son obligatorios"
    });
  }

  // 2. Crear entidad con ID incremental
  const nuevo = {
    id: productos.length ? Math.max(...productos.map(p => p.id)) + 1 : 1,
    nombre: nombre.trim(),
    precio: Number(precio),
    categoria: (categoria || "GENERAL").toUpperCase(),
    stock: Number(stock) || 0
  };

  productos.push(nuevo);
  // 3. Responder 201 Created
  res.status(201).json({ ok: true, dato: nuevo });
});

Siempre responde 201 al crear entidades; reservar 200 para lecturas y actualizaciones.

BLOQUE 2 Arquitectura REST · Comparativa de Modificación
SLIDE 14 / 21

Idempotencia en Acción: PUT vs PATCH

Una de las preguntas más frecuentes en pruebas técnicas de desarrollo backend es: "¿Cuándo debo usar PUT y cuándo debo usar PATCH?"

PUT

Reemplazo Completo

IDEMPOTENTE

Sobrescribe el recurso en su totalidad. El cliente debe enviar todos los campos obligatorios de la entidad. Si omites un campo (ej. stock), ese campo se elimina o se resetea a nulo.

// Payload PUT /api/productos/1 (Requiere TODO)
{
  "nombre": "Teclado RGB Pro",
  "precio": 140000,
  "categoria": "HARDWARE",
  "stock": 10
}
Si se ejecuta 10 veces, el estado final es exactamente idéntico.
PATCH

Modificación Parcial

DELTA / DELICADO

Aplica cambios incrementales o atómicos únicamente sobre las propiedades enviadas. El resto de propiedades del objeto se conservan intactas en la base de datos.

// Payload PATCH /api/productos/1/stock (Solo envía lo que cambia)
{
  "nuevoStock": 25
}
Ideal para cambiar estado, actualizar inventario o publicar un artículo.

BLOQUE 2 Endpoint 4 · Modificación Parcial con PATCH
SLIDE 15 / 21

Endpoint 4: PATCH /api/productos/:id/stock

Aquí combinamos dos fuentes de datos en la misma petición: el ID del producto que viaja en req.params.id y el nuevo valor de inventario que viaja en req.body.nuevoStock.

Código Express.js Params + Body 
app.patch('/api/productos/:id/stock', (req, res) => {
  const id = Number(req.params.id);
  const { nuevoStock } = req.body;

  // 1. Validar producto existente (404)
  const producto = productos.find(p => p.id === id);
  if (!producto) {
    return res.status(404).json({ ok: false, error: "Producto no encontrado" });
  }

  // 2. Validar payload numérico (400)
  if (typeof nuevoStock !== 'number' || nuevoStock < 0) {
    return res.status(400).json({ ok: false, error: "nuevoStock debe ser >= 0" });
  }

  const anterior = producto.stock;
  producto.stock = nuevoStock; // Mutación controlada

  res.status(200).json({
    ok: true,
    mensaje: "Stock actualizado correctamente",
    stockAnterior: anterior,
    stockActual: producto.stock
  });
});

Validar que nuevoStock no sea un string protege contra datos corruptos.

BLOQUE 2 Endpoint 5 · Eliminación Segura e Idempotente
SLIDE 16 / 21

Endpoint 5: DELETE /api/productos/:id (200 vs 404)

Para eliminar registros buscamos la posición del elemento con findIndex() y lo removemos con splice(). Si ya no existe, debemos retornar 404 Not Found.

Código Express.js Búsqueda y Eliminación 
app.delete('/api/productos/:id', (req, res) => {
  const id = Number(req.params.id);
  const index = productos.findIndex(p => p.id === id);

  // 1. Si no existe, responder 404
  if (index === -1) {
    return res.status(404).json({
      ok: false,
      error: `Producto con ID ${id} no encontrado para eliminar`
    });
  }

  // 2. Eliminar elemento del array
  const [eliminado] = productos.splice(index, 1);

  // 3. Responder 200 OK con el registro eliminado
  res.status(200).json({
    ok: true,
    mensaje: "Producto eliminado exitosamente",
    dato: eliminado
  });
});

También es válido según la RFC responder 204 No Content con res.status(204).send().

BLOQUE 2 Express.js · Control Global de Rutas
SLIDE 17 / 21

Manejo Global de Rutas 404: Middleware Catch-All

¿Qué ocurre si un cliente solicita una ruta que nunca registramos (ej. /api/inventario)? Si no configuramos un middleware final, Express responderá con una página HTML predeterminada de error. En APIs profesionales siempre debemos responder en formato JSON.

Ubicación Obligatoria en server.js Al final de todas las rutas 
// ... todas las rutas GET, POST, PATCH, DELETE ...

// MIDDLEWARE CATCH-ALL PARA RUTAS NO REGISTRADAS
app.use((req, res) => {
  res.status(404).json({
    ok: false,
    error: "Endpoint no encontrado en el servidor ADSO",
    metodo: req.method,
    rutaSolicitada: req.originalUrl,
    sugerencia: "Consulte la documentación de la API en /api/status"
  });
});

// Al final absoluto:
app.listen(PORT, () => ...);

Al no especificar ruta (app.use(handler)), intercepta cualquier verbo y cualquier URL que no haya coincidido arriba.

BLOQUE 3 Evaluación en Tiempo Real · Live Mod
SLIDE 20 / 21

Live Mod: La Prueba de Fuego Individual

Para garantizar la autoría individual y la agilidad técnica, cada aprendiz proyectará su servidor y resolverá en caliente (15 minutos) una modificación imprevista solicitada por el docente.

Dinámica ante el Videobeam

  1. 1. El aprendiz comparte pantalla con su código en VS Code y su colección en Bruno.
  2. 2. El docente asigna un reto sorpresa del banco de modificaciones.
  3. 3. El aprendiz tiene 15 minutos para codificar la lógica, guardar y probarla exitosamente en Bruno en vivo.
  4. 4. El aprendiz debe justificar verbalmente qué Status Code eligió y por qué.
25% de la Calificación de la Sesión
BANCO DE RETOS POSIBLES (ALEATORIOS) Instructor ADSO
  • Reto A: Filtro de precio máximo GET /api/productos?precioMax=50000 retornando solo productos con precio menor o igual.
  • Reto B: Endpoint GET /api/productos/agotados que retorne exclusivamente productos con stock === 0.
  • Reto C: Endpoint PUT /api/productos/:id para reemplazo completo exigiendo todos los campos del producto con validación 400.
  • Reto D: Validación en POST que impida crear productos con SKU duplicado (retornando 409 Conflict).

Cada aprendiz recibirá una variante diferente según su modelo de datos.

El Live Mod valida que el aprendiz comprende la arquitectura y no solo completó código de memoria.
