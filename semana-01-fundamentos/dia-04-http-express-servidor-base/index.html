El Ciclo Request - Response: Arquitectura Cliente-Servidor

HTTP (Hypertext Transfer Protocol) es el protocolo de capa de aplicación sobre TCP/IP que rige la web. Es un modelo Stateless (sin estado): el servidor atiende cada petición de forma aislada sin recordar quién fuiste hace un segundo.

1. Cliente (Consumer)

Navegador web, app móvil en React Native o un cliente como Bruno. Empaqueta el método, la URL de destino, encabezados y datos en un mensaje estándar HTTP.

Petición (HTTP Request)

2. Servidor (Node / Express)

Escucha en un socket/puerto (ej. 3000). El Event Loop recibe el stream TCP, lo parsea mediante middlewares (express.json()), ejecuta la lógica del controlador y prepara la respuesta.

Procesamiento Stateless

3. Respuesta (HTTP Response)

El backend retorna un código de estado numérico (200, 201, 404, 500), encabezados de respuesta (Content-Type: application/json) y el cuerpo con los datos serializados.

Payload JSON Estructurado
Regla de Oro en Backend: Toda petición HTTP debe recibir una respuesta (`res.json()` o `res.send()`). Si olvidas responder, el cliente quedará colgado hasta dar timeout.
Stateless Architecture

Anatomía de Peticiones y Respuestas: Headers & MIME Types

Un mensaje HTTP es texto plano transmitido por la red. Los Headers (encabezados) son metadatos clave que definen el formato de codificación, seguridad y autenticación.

Host: localhost:3000
Content-Type: application/json

User-Agent: Bruno/1.25.0

{
  "sku": "TEC-01",
  "nombre": "Teclado Mecánico",
  "precio": 120000

Verbos HTTP & Filosofía REST: Semántica e Idempotencia

En arquitectura REST, las URLs representan recursos en sustantivo (ej. /api/productos) y los Verbos HTTP determinan la acción a realizar.

GET

Lectura

Obtiene recursos. Seguro e Idempotente: ejecutarlo 100 veces no muta los datos del servidor.

app.get()
POST

Creación

Crea nuevos registros con req.body. No idempotente: cada envío genera un nuevo registro.

app.post()
PUT

Reemplazo

Reemplaza el objeto completo en /:id. Exige enviar todas las propiedades del recurso.

app.put()
PATCH

Parcial

Actualiza solo una o varias propiedades específicas (ej. solo el stock o el precio) sin reenviar todo.

app.patch()
DELETE

Eliminación

Elimina el recurso identificado por /:id (borrado físico o borrado lógico).

app.delete()
❌ Anti-patrón común en aprendices: Nombrar rutas como /api/eliminarProducto o /api/crearUsuario. En REST se usa siempre DELETE /api/productos/:id y POST /api/usuarios. RESTful Naming

SLIDE 05 / 15

Códigos de Estado HTTP: Las Familias Semánticas

El Status Code es un número entero de 3 dígitos que le dice al cliente de forma instantánea el resultado de la operación sin necesidad de parsear el cuerpo del mensaje.

2xx SUCCESS Operación Exitosa
  • 200 OK: Petición exitosa estándar (lectura con GET, actualización con PUT/PATCH).
  • 201 Created: Registro creado exitosamente en base de datos mediante POST.
  • 204 No Content: Éxito sin cuerpo de respuesta (muy común en DELETE).
4xx CLIENT ERROR Culpa del Cliente
  • 400 Bad Request: Payload inválido, faltan campos requeridos o tipos erróneos.
  • 404 Not Found: El recurso con ese ID o la ruta solicitada no existe.
  • 409 Conflict: Violación de restricción única (ej. SKU o correo ya registrado).
5xx SERVER ERROR Fallo Interno
  • 500 Internal Error: Excepción no controlada en el backend (bug de código o caída de BD).
  • 502 Bad Gateway: El servidor proxy o gateway no recibió respuesta válida.
  • 503 Unavailable: Servidor sobrecargado o en mantenimiento temporal.
⚠️ Prohibido en ADSO: Retornar HTTP 200 con un cuerpo `{ error: "No encontrado" }`. Usa el código HTTP correspondiente: `res.status(404).json(...)`. Semantic Status

Inicialización del Proyecto: ESM vs CommonJS

Históricamente Node.js utilizó CommonJS (const express = require('express');). En el estándar moderno 2026 configuramos "type": "module" en package.json para usar sintaxis oficial import/export.

Flujo de Inicialización en Terminal:

# 2. Instalar el framework Express

npm install express

# 3. Arrancar el servidor

node server.js

  }

BLOQUE 1 Arquitectura Express.js
SLIDE 07 / 15

Servidor Base Express: Instancia & Puerto de Escucha

Express es el framework de servidor web más consolidado en el ecosistema Node.js. Provee una capa minimalista sobre el módulo HTTP nativo facilitando el enrutamiento y la composición mediante middlewares.

Anatomía del Servidor Mínimo:

  • 1 Importación: Se importa la función factoría import express from 'express';.
  • 2 Instanciación: const app = express(); crea la aplicación que manejará las rutas y ciclo de vida.
  • 3 Puerto Dinámico: const PORT = process.env.PORT || 3000; necesario para despliegues en la nube (Railway/Render).
  • 4 Escucha de Red: app.listen(PORT, callback) abre el socket TCP y queda a la espera de peticiones entrantes.
server.js (Servidor Base) ESM Express 
import express from 'express';

const app = express();
const PORT = process.env.PORT || 3000;

// Ruta raíz de comprobación:
app.get('/', (req, res) => {
  res.send('Servidor Express SENA ADSO activo');
});

// Poner en marcha la escucha del puerto:
app.listen(PORT, () => {
  console.log(`Servidor corriendo en: http://localhost:${PORT}`);
});
TCP Socket Binding Ready for requests
Siempre define el puerto con process.env.PORT || 3000. En producción las plataformas de hosting asignan puertos aleatorios. Cloud Ready

SLIDE 08 / 15

El Middleware express.json(): De Bytes a Objeto

Por defecto, Express NO procesa el cuerpo de las peticiones HTTP porque viajan como fragmentos binarios (*streams*). Sin este middleware, req.body será siempre undefined.

¿Qué ocurre internamente en la tubería?

1. Inspecciona el Header:

Verifica si la petición contiene el encabezado Content-Type: application/json.

2. Ensambla el Stream:

Concatena los buffers de datos que van llegando por la red en memoria.

3. Inyecta en req.body:

Ejecuta JSON.parse() de forma segura y monta el objeto resultante en req.body para que tus rutas lo consuman limpiamente.

middleware_flow.js app.use(express.json()) 
import express from 'express';

const app = express();

// 🛡️ Middleware OBLIGATORIO antes de las rutas:
app.use(express.json());

// Endpoint de prueba:
app.post('/api/pedidos', (req, res) => {
  // ✅ Gracias a express.json(), req.body existe:
  console.log('Datos recibidos:', req.body);
  
  const { cliente, total } = req.body;
  res.status(201).json({ ok: true, cliente, total });
});
Pipeline de Middlewares req.body parsed
⚠️ Coloca siempre app.use(express.json()) antes de definir tus rutas. Los middlewares en Express se ejecutan en estricto orden secuencial. Middleware Order

SLIDE 09 / 15

Captura de Parámetros I: req.params (Rutas Dinámicas)

Los parámetros de ruta se declaran anteponiendo dos puntos (:nombreParametro). Se utilizan para identificar un recurso único dentro de la colección.

Reglas de Implementación en ADSO:

  • 1. Siempre vienen como String: req.params.id es una cadena. Para buscar en un array o base de datos relacional debes convertirlo con Number(req.params.id).
  • 2. Validación de Existencia: Si el registro no existe, responde de inmediato con status 404 Not Found.
  • 3. Validación de Tipo: Si envían /api/productos/abc, valida con isNaN(id) y retorna 400 Bad Request.
URL Ejemplo: GET http://localhost:3000/api/productos/3
➔ req.params produce: { id: "3" }
params_handler.js req.params 
app.get('/api/productos/:id', (req, res) => {
  const id = Number(req.params.id);

  if (isNaN(id)) {
    return res.status(400).json({
      ok: false,
      error: 'El ID proporcionado debe ser un número entero'
    });
  }

  const producto = inventario.find(p => p.id === id);

  if (!producto) {
    return res.status(404).json({
      ok: false,
      error: `Producto con ID ${id} no encontrado`
    });
  }

  res.status(200).json({ ok: true, datos: producto });
});

SLIDE 10 / 15

Captura de Parámetros II: req.query (Filtros & Búsqueda)

Los Query Strings viajan al final de la URL precedidos por un signo de interrogación (?clave=valor&otra=123). Son opcionales y se emplean para filtrar, ordenar y paginar listas de recursos.

Diferencia Clave: Params vs Query

req.params (Obligatorio en la ruta):

Identifica el recurso específico: /api/productos/42

req.query (Opcional en la ruta):

Filtra la colección: /api/productos?categoria=HARDWARE&q=rgb

URL Ejemplo: GET /api/productos?categoria=HARDWARE&q=teclado
➔ req.query produce: { categoria: "HARDWARE", q: "teclado" }
query_filter.js req.query 
app.get('/api/productos', (req, res) => {
  const { categoria, q } = req.query;
  let listado = [...inventario];

  // Filtro por categoría (si se proporcionó):
  if (categoria) {
    listado = listado.filter(p => 
      p.categoria.toUpperCase() === categoria.toUpperCase()
    );
  }

  // Búsqueda por texto (si se proporcionó):
  if (q) {
    const texto = q.toLowerCase();
    listado = listado.filter(p => 
      p.nombre.toLowerCase().includes(texto)
    );
  }

  res.status(200).json({
    ok: true,
    total: listado.length,
    datos: listado
  });
});
Búsqueda Flexible y Filtrado 200 OK
En el cliente Bruno podemos definir y activar/desactivar Query Params con casillas de verificación en la pestaña Params. Bruno Integration
BLOQUE 1 Creación y Mutación de Datos
SLIDE 11 / 15

Captura de Parámetros III: req.body (Validación & 201 Created)

En los métodos POST y PUT los datos viajan en el cuerpo de la petición. El backend debe actuar como un guardia fronterizo: nunca confíes en los datos del cliente.

Checklist de Validación Defensiva:

  • 1 Campos obligatorios: Si falta nombre, precio o sku ➔ Rechazar inmediatamente con 400 Bad Request.
  • 2 Reglas de negocio: Precios mayores a cero, existencias no negativas.
  • 3 Unicidad: Si el SKU ya existe ➔ Rechazar con 409 Conflict.
  • 4 Éxito de Creación: Responder con código 201 Created y devolver el registro recién guardado con su nuevo ID.
post_handler.js POST 201 Created 
app.post('/api/productos', (req, res) => {
  const { sku, nombre, precio, stock } = req.body;

  // 1. Validación de presencia:
  if (!sku || !nombre || precio === undefined) {
    return res.status(400).json({
      ok: false,
      error: 'sku, nombre y precio son campos requeridos'
    });
  }

  // 2. Creación con ID único:
  const nuevo = {
    id: Date.now(),
    sku: sku.toUpperCase(),
    nombre: nombre.trim(),
    precio: Number(precio),
    stock: Number(stock || 0)
  };

  inventario.push(nuevo);

  // 3. Respuesta 201 Created:
  res.status(201).json({
    ok: true,
    mensaje: 'Producto creado exitosamente',
    datos: nuevo
  });
});
Validación de Integridad 201 Created
El Reto 5 del taller evalúa la capacidad de rechazar entradas maliciosas o incompletas con 400 Bad Request antes de persistirlas. Reto 5 Focus

Manejo de Errores & Middleware Global 404 Catch-All

Si un cliente solicita una ruta no registrada (ej. /api/usuarios), el comportamiento por defecto de Express devuelve un HTML feo "Cannot GET /api/usuarios". En una API REST siempre debemos responder en JSON estructurado.

¿Cómo funciona el Middleware Catch-All?

Express evalúa las rutas registradas en orden de arriba hacia abajo. Si ninguna ruta coincide con el método o la URL solicitada, la ejecución llega al último middleware:

⚠️ Regla Estricta de Ubicación:

El middleware 404 debe ubicarse al final de todas las rutas válidas, justo antes de app.listen(). Si lo colocas arriba, interceptará todas las peticiones antes de tiempo.

error_middleware.js Catch-All 404 
// Rutas válidas arriba...
app.get('/api/productos', ...);
app.post('/api/productos', ...);

// 🛡️ Middleware final para rutas NO mapeadas:
app.use((req, res) => {
  res.status(404).json({
    ok: false,
    error: `La ruta '${req.originalUrl}' no existe en este servidor`,
    metodo: req.method,
    sugerencia: 'Endpoints válidos en /api/status o /api/productos'
  });
});

app.listen(PORT, ...);
Zero Unhandled Routes JSON 404
Esto asegura que clientes frontend o móviles reciban siempre JSON procesable y no errores de parseo por respuestas HTML. API Consistency

Cliente de APIs: Bruno vs Postman & Insomnia

Para probar endpoints backend antes de construir la interfaz gráfica necesitamos un cliente HTTP. En SENA ADSO usamos Bruno: un cliente de código abierto, ultraligero y diseñado para vivir dentro de Git.

1. Colecciones en Git (.bru)

Bruno no guarda peticiones en nubes de terceros. Cada endpoint es un archivo de texto plano .bru guardado en tu carpeta de proyecto y versionado con git commit.

2. Local-First & Sin Cuenta

No requiere iniciar sesión, crear cuenta corporativa ni estar conectado a internet. Ideal para las salas de informática y desarrollo offline de alta velocidad.

3. Variables de Entorno

Define {{baseUrl}} para apuntar a http://localhost:3000 en local y cambiar a producción en un clic sin modificar peticiones individuales.

Cómo abrir en clase: En Bruno haz clic en Open Collection ➔ Selecciona la carpeta recursos/bruno-collection/.
