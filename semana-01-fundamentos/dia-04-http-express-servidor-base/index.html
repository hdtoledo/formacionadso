El Ciclo Request - Response: Arquitectura Cliente-Servidor

HTTP (Hypertext Transfer Protocol) es el protocolo de capa de aplicación sobre TCP/IP que rige la web. Es un modelo Stateless (sin estado): cada interacción es independiente y el servidor no guarda memoria implícita de la petición anterior.

1. Cliente (Consumer)

Un navegador web, una app móvil o un cliente de pruebas (Bruno / Postman). Inicia la conexión resolviendo el DNS, establece un socket TCP y envía un paquete formateado en texto plano.

HTTP Request (Petición)

2. Servidor (Node / Express)

Escucha en un socket/puerto (ej. 3000). El Event Loop recibe el stream TCP, lo parsea mediante middlewares (express.json()), ejecuta la lógica del controlador y prepara la respuesta.

Procesamiento Stateless

3. Respuesta (HTTP Response)

El backend retorna un código de estado numérico (200, 201, 404, 500), encabezados de respuesta (Content-Type: application/json) y el cuerpo con los datos serializados.

Payload JSON Estructurado
Regla de Oro en Backend: Toda petición HTTP debe recibir una respuesta (res.json() o res.send()). Si olvidas responder, el cliente quedará colgado hasta dar timeout.
Stateless Architecture

Anatomía de Peticiones y Respuestas: Headers & MIME Types

Un mensaje HTTP es texto plano transmitido por la red. Los Headers (encabezados) son metadatos clave que definen el formato de codificación, seguridad y autenticación.

HTTP REQUEST (Cliente ➔ Servidor) Petición POST 
POST /api/productos HTTP/1.1
Host: localhost:3000
Content-Type: application/json
Accept: application/json
User-Agent: Bruno/1.25.0

{
  "sku": "TEC-01",
  "nombre": "Teclado Mecánico",
  "precio": 120000
}

Línea de Inicio: Método (POST) + Ruta (/api/productos) + Protocolo.

Content-Type: Avisa a Express que el body viene en formato JSON.

HTTP RESPONSE (Servidor ➔ Cliente) Respuesta 201 Created 
HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Content-Length: 142
Date: Tue, 15 Sep 2026 14:30:00 GMT

{
  "ok": true,
  "mensaje": "Producto registrado exitosamente",
  "datos": { "id": 6, "sku": "TEC-01", "precio": 120000 }
}

Línea de Estado: Protocolo + Código de Estado (201) + Frase (Created).

Body Serializado: Objeto JSON devuelto al cliente que originó la petición.

Content-Type Indica el tipo MIME de los datos que viajan en el cuerpo: application/json, multipart/form-data.
Accept El cliente declara qué formato espera recibir del backend: Accept: application/json.
Authorization Transporta credenciales o tokens de seguridad: Bearer eyJhbGciOi....

Verbos HTTP & Filosofía REST: Semántica e Idempotencia

En arquitectura REST, las URLs representan recursos en sustantivo (ej. /api/productos) y los Verbos HTTP determinan la acción a realizar.

Verbo HTTP Propósito REST ¿Tiene Body? Idempotente Seguro (Safe) Ejemplo en Express
GET Lectura y consulta de recursos No Sí Sí (no muta) app.get('/api/productos', ...)
POST Creación de un nuevo recurso Sí (Payload) No (crea N veces) No (muta BD) app.post('/api/productos', ...)
PUT Reemplazo total de un recurso existente Sí (Todo el objeto) Sí No (muta BD) app.put('/api/productos/:id', ...)
PATCH Modificación parcial de campos específicos Sí (Campos clave) Depende No (muta BD) app.patch('/api/productos/:id/stock', ...)
DELETE Eliminación de un recurso por su ID Rara vez Sí No (muta BD) app.delete('/api/productos/:id', ...)
Antipatrón a evitar en el SENA: Jamás uses verbos en la URL como /api/crearProducto o /api/eliminarProducto/5. La URL siempre debe ser el sustantivo /api/productos y el verbo HTTP (POST o DELETE) define la acción.

Códigos de Estado HTTP: Las Familias Semánticas

El Status Code es un número entero de 3 dígitos que le dice al cliente de forma instantánea el resultado de la operación sin necesidad de parsear el cuerpo de la respuesta.

2xx SUCCESS Éxito
  • 200 OK Respuesta exitosa estándar para peticiones GET, PUT o PATCH.
  • 201 Created Obligatorio tras un POST exitoso que da vida a un nuevo recurso con su ID asignado.
  • 204 No Content Operación exitosa pero sin cuerpo de retorno (muy común en respuestas DELETE).

El frontend continúa su flujo normal.

4xx CLIENT ERROR Error del Cliente
  • 400 Bad Request El cliente envió datos mal formados, omitió campos obligatorios o envió tipos erróneos.
  • 404 Not Found El ID buscado o la URL solicitada no existe en el catálogo ni en las rutas del servidor.
  • 409 Conflict Violación de restricción única (ej. SKU o correo ya registrado en la base de datos).

El cliente debe corregir los datos antes de reintentar.

5xx SERVER ERROR Fallo Interno
  • 500 Internal Server Error Ocurrió una excepción no controlada en el código Node.js (ej. TypeError: Cannot read property of undefined).
  • 503 Service Unavailable El servidor está caído, en mantenimiento o la base de datos no responde a la conexión.

Es responsabilidad del desarrollador backend corregir el bug.

res.status(201).json({ ok: true, datos: nuevoRecurso }) Siempre encadena el código antes de serializar con .json()

BLOQUE 1 Arquitectura Express.js
SLIDE 07 / 20

Servidor Base Express: Instancia & Puerto de Escucha

Express es el framework de servidor web minimalista por excelencia en Node.js. Provee una API declarativa para enlazar métodos HTTP con rutas y controladores mediante (req, res).

servidor.js Instanciación Mínima 
import express from 'express';

// 1. Crear la instancia de la aplicación Express
const app = express();

// 2. Definir el puerto (usando variable de entorno o puerto 3000 por defecto)
const PORT = process.env.PORT || 3000;

// 3. Registrar un endpoint de diagnóstico (Health Check)
app.get('/api/status', (req, res) => {
  res.status(200).json({
    ok: true,
    mensaje: "Servidor Express ADSO en funcionamiento",
    uptime: Math.floor(process.uptime()),
    timestamp: new Date().toISOString()
  });
});

// 4. Abrir el socket TCP y escuchar peticiones entrantes
app.listen(PORT, () => {
  console.log(`🚀 Servidor Express activo en: http://localhost:${PORT}`);
});

Componentes Vitales

app = express()

Instancia central que gestiona el enrutador de peticiones y la pila de middlewares.

(req, res)

req contiene los datos de entrada del cliente; res provee los métodos para enviar la respuesta HTTP.

app.listen(PORT)

Vincula el proceso de Node.js a un puerto TCP del sistema operativo para escuchar tráfico de red.

Salida esperada en terminal:
🚀 Servidor Express activo en: http://localhost:3000
Buenas Prácticas SENA: Siempre lee el puerto con process.env.PORT || 3000 para que tu backend sea compatible con despliegues en la nube (Render, Railway o AWS). 12-Factor App

El Middleware express.json(): De Bytes a Objeto JS

Por defecto, Express NO procesa el cuerpo de las peticiones HTTP entrantes porque viajan como fragmentos binarios (*streams* de red). Sin este middleware, req.body será undefined.

❌ SIN app.use(express.json()) Error Común

Si envías un JSON desde Bruno o el frontend a un endpoint POST: 

app.post('/api/productos', (req, res) => {
  console.log(req.body); 
  // ⚠️ IMPRIME: undefined
  
  const { nombre } = req.body;
  // 💥 TypeError: Cannot destructure property 
  // 'nombre' of undefined or null
});
El servidor se rompe o arroja excepción 500 por falta del parser de cuerpo.
✅ CON app.use(express.json()) Requerido

Express intercepta el stream, espera todos los bytes y construye el objeto JavaScript: 

// Registrar OBLIGATORIAMENTE antes de las rutas:
app.use(express.json());

app.post('/api/productos', (req, res) => {
  console.log(req.body); 
  // ✅ IMPRIME: { sku: 'TEC-01', precio: 120000 }
  
  const { sku, precio } = req.body;
  // Datos listos para validar y almacenar
});
Transforma automáticamente el payload JSON en un objeto JS disponible en req.body.
⚠️ REGLA DE ORDEN: Debes invocar app.use(express.json()) antes de definir cualquier ruta POST, PUT o PATCH. Los middlewares se ejecutan en estricto orden de registro.

Captura de Parámetros I: req.params (Rutas Dinámicas)

Los parámetros de ruta se declaran anteponiendo dos puntos (:nombreParametro). Se utilizan para identificar y operar sobre un recurso específico dentro de la colección.

GET /api/productos/:id 200 OK vs 404 Not Found 
app.get('/api/productos/:id', (req, res) => {
  // 1. OBLIGATORIO: Convertir el parámetro a número
  const id = Number(req.params.id);

  if (isNaN(id)) {
    return res.status(400).json({ ok: false, error: "El ID debe ser numérico" });
  }

  // 2. Buscar en la colección de memoria con .find()
  const producto = productos.find(p => p.id === id);

  // 3. Si no existe, responder inmediatamente con 404
  if (!producto) {
    return res.status(404).json({
      ok: false,
      error: `Producto con ID ${id} no encontrado en el catálogo`
    });
  }

  // 4. Si existe, responder 200 OK con el objeto
  res.status(200).json({
    ok: true,
    datos: producto
  });
});

Análisis Técnico

🚨 La Trampa del String req.params.id siempre es un string (ej. "1"). Si comparas con triple igual: p.id === req.params.id // 1 === "1" (FALSE) Por eso es obligatorio usar Number(req.params.id).
Estructura de la URL: http://localhost:3000/api/productos/2 El valor 2 se asigna a req.params.id.
Status 200 / 404 Semantic REST
Principio de Guard Clause: Valida primero el error y haz return res.status(...) temprano para evitar anidar bloques else innecesarios. Clean Code Backend

Captura de Parámetros II: req.query (Filtros & Búsqueda)

Los Query Strings viajan al final de la URL precedidos por un signo de interrogación (?clave=valor&otra=123). Son opcionales y se emplean para filtrar, ordenar o paginar colecciones.

GET /api/productos?categoria=HARDWARE&q=teclado Filtro Dinámico 
app.get('/api/productos', (req, res) => {
  // 1. Extraer los query parameters mediante destructuración
  const { categoria, q } = req.query;

  // 2. Crear una copia inmutable del catálogo
  let resultado = [...productos];

  // 3. Aplicar filtro por categoría si fue enviada por el cliente
  if (categoria) {
    resultado = resultado.filter(p => 
      p.categoria.toUpperCase() === categoria.toUpperCase()
    );
  }

  // 4. Aplicar búsqueda por texto (nombre o SKU) si fue enviada
  if (q) {
    const termino = q.toLowerCase();
    resultado = resultado.filter(p => 
      p.nombre.toLowerCase().includes(termino) || 
      p.sku.toLowerCase().includes(termino)
    );
  }

  // 5. Retornar siempre 200 OK con los resultados y metadatos
  res.status(200).json({
    ok: true,
    total: resultado.length,
    filtrosAplicados: { categoria: categoria || null, q: q || null },
    datos: resultado
  });
});

Diferencia Clave

req.params (Obligatorio en ruta) /api/productos/:id Identifica un único recurso específico. Si no se envía el ID, la ruta no coincide (404).
req.query (Opcional en URL) /api/productos?categoria=X Modifica la presentación de la lista. Si no se envían, la ruta responde con toda la colección.
Si la búsqueda no arroja coincidencias, retorna 200 OK con datos: [] (nunca 404).
Principio REST: Una búsqueda sin resultados sigue siendo una consulta exitosa. Debe devolver 200 OK con un array vacío, no un error 404. API Design Standard

Captura de Parámetros III: req.body (Validación & 201 Created)

En los métodos POST y PUT los datos viajan en el cuerpo de la petición. El backend debe actuar como un guardia fronterizo: nunca confíes en los datos enviados por el cliente.

POST /api/productos Validación Defensiva en 4 Pasos 
app.post('/api/productos', (req, res) => {
  // 1. Extraer los campos esperados del cuerpo
  const { sku, nombre, categoria, stock, precio } = req.body;

  // 2. Validación de presencia: Ningún campo puede faltar
  if (!sku || !nombre || !categoria || stock === undefined || precio === undefined) {
    return res.status(400).json({
      ok: false,
      error: "Todos los campos (sku, nombre, categoria, stock, precio) son obligatorios."
    });
  }

  // 3. Validación de unicidad: El SKU no puede repetirse
  const yaExiste = productos.some(p => p.sku.toUpperCase() === sku.toUpperCase());
  if (yaExiste) {
    return res.status(409).json({
      ok: false,
      error: `Conflicto: Ya existe un producto con el SKU '${sku}'`
    });
  }

  // 4. Instanciar el nuevo producto y responder con 201 Created
  const nuevoProducto = {
    id: Date.now(), // ID único
    sku: sku.trim().toUpperCase(),
    nombre: nombre.trim(),
    categoria: categoria.trim().toUpperCase(),
    stock: Number(stock),
    precio: Number(precio)
  };

  productos.push(nuevoProducto);

  res.status(201).json({
    ok: true,
    mensaje: "Producto registrado exitosamente en el inventario",
    datos: nuevoProducto
  });
});

Lógica de Códigos

400 Bad Request Se devuelve cuando faltan atributos o no cumplen el formato esperado. Evita insertar registros corruptos en memoria o base de datos.
409 Conflict Indica que la petición colisiona con el estado actual del servidor (ej. duplicación de llave única / SKU).
201 Created Obligatorio según el estándar HTTP cuando la creación es exitosa y se ha instanciado un recurso nuevo.
Status 400 ➔ Status 409 ➔ Status 201
Sanitización con Trim: Aplica .trim() a los strings para limpiar espacios accidentales antes de guardarlos. Defensive Programming

Actualización en Caliente: PATCH vs PUT

¿Cuándo usar PATCH y cuándo PUT? En operaciones de inventario o cambio de estado, enviar el objeto completo por la red es ineficiente y riesgoso.

PATCH /api/productos/:id/stock Modificación Parcial 
app.patch('/api/productos/:id/stock', (req, res) => {
  const id = Number(req.params.id);
  const { nuevoStock } = req.body;

  // 1. Validar que el stock sea un número válido y >= 0
  const stockNum = Number(nuevoStock);
  if (nuevoStock === undefined || isNaN(stockNum) || stockNum < 0) {
    return res.status(400).json({
      ok: false,
      error: "Debe proveer un valor numérico 'nuevoStock' mayor o igual a 0."
    });
  }

  // 2. Localizar el producto en memoria
  const producto = productos.find(p => p.id === id);
  if (!producto) {
    return res.status(404).json({
      ok: false,
      error: `Producto con ID ${id} no encontrado para actualizar stock.`
    });
  }

  // 3. Mutar quirúrgicamente solo la propiedad 'stock'
  const stockAnterior = producto.stock;
  producto.stock = stockNum;

  // 4. Responder con 200 OK y auditoría del cambio
  res.status(200).json({
    ok: true,
    mensaje: `Stock actualizado para '${producto.nombre}'`,
    datos: { id: producto.id, stockAnterior, stockActual: producto.stock }
  });
});

Comparativa REST

PATCH (Quirúrgico) Envía solo los campos modificados en el body: 
{ "nuevoStock": 15 }
Ideal para controles rápidos de inventario, switches de estado activo/inactivo o cambios puntuales.
PUT (Reemplazo Total) Requiere enviar la entidad completa: 
{ "sku": "...", "nombre": "...", ... }
Si omites un campo en el body, la convención REST indica que ese campo debe borrarse o quedar nulo.
Semántica de Modificación
Eficiencia de Red: PATCH reduce el consumo de ancho de banda al transmitir únicamente los bytes de los campos que sufrieron alteración. Network Optimization

Manejo de Errores & Middleware Global 404 Catch-All

Si un cliente solicita una ruta no registrada (ej. /api/usuarios), el comportamiento por defecto de Express devuelve un HTML plano Cannot GET /api/usuarios. En una API REST profesional, toda respuesta debe ser JSON.

Middleware Catch-All en Express Respuesta JSON Uniforme 
// ... (Todos los app.get, app.post, app.patch van arriba)

// =======================================================
// MIDDLEWARE 404 GLOBAL (DEBE SER EL ÚLTIMO EN REGISTRARSE)
// =======================================================
app.use((req, res) => {
  res.status(404).json({
    ok: false,
    error: `Ruta no encontrada: [${req.method}] ${req.originalUrl}`,
    sugerencia: "Consulta los endpoints disponibles en /api/status o /api/productos",
    timestamp: new Date().toISOString()
  });
});
Al no especificar una ruta (sin string en el primer argumento), este middleware intercepta cualquier petición que haya atravesado la pila sin hacer match previo.

¿Por qué el orden es vital?

Express procesa las peticiones en una tubería secuencial (Pipeline de Middlewares):

  1. 1. Ejecuta express.json() para parsear el body.
  2. 2. Evalúa las rutas registradas (/api/status, /api/productos, etc.).
  3. 3. Si ninguna ruta coincidió, cae en el Middleware 404.
🚨 ERROR FATAL: Si colocas app.use((req, res) => ...) al inicio de tu código, atrapará todas las peticiones y tus endpoints jamás se ejecutarán.
Pipeline Middleware Order
Formato Uniforme: Tanto las respuestas exitosas como los errores deben compartir una estructura predecible: { ok: false, error: "..." }. API Contract Consistency

Cliente de APIs: Bruno vs Postman & Insomnia

Para probar endpoints backend antes de construir la interfaz gráfica necesitamos un cliente HTTP. En SENA ADSO usamos Bruno: un cliente moderno, de código abierto y diseñado con filosofía Local-First.

Bruno (Elección Oficial ADSO)

Recomendado
  • 100% Local y Offline: No requiere crear cuenta, login ni conexión a servidores externos.
  • Formato Plain-Text (.bru): Las peticiones son archivos de texto guardados directamente en la carpeta de tu proyecto.
  • Control de Versiones Nativo: Haces git add y git commit de tus peticiones junto al código de tu servidor Express.
  • Ligero y Rápido: Consume una fracción minúscula de memoria RAM comparado con Postman.
Descarga gratuita en: usebruno.com

Postman / Insomnia (Tradicional)

Legacy
  • Obliga a Iniciar Sesión en la Nube: Si la red del centro de formación falla, no puedes acceder a tus colecciones de trabajo.
  • Colecciones Desconectadas de Git: Obliga a exportar manualmente pesados archivos JSON que provocan conflictos al mergear en equipo.
  • Alto Consumo de Recursos: Aplicación pesada basada en Electron con telemetría continua.
Desaconsejado para repositorios colaborativos

Live Coding Guiado: El Flujo Completo en Vivo

Observa en el videobeam cómo conectamos un nuevo endpoint en Express, guardamos el archivo y lo probamos instantáneamente en Bruno:

// Reto Bonus: Eliminar producto por ID
app.delete('/api/productos/:id', (req, res) => {
  const id = Number(req.params.id);

  const indice = productos.findIndex(p => p.id === id);
  if (indice === -1) {
    return res.status(404).json({
      ok: false,
      error: `Producto con ID ${id} no encontrado`
    });
  }

  const [eliminado] = productos.splice(indice, 1);

  res.status(200).json({
    ok: true,
    mensaje: "Producto eliminado exitosamente",
    datos: eliminado
  });
});
